# 第二阶段：设备身份、账号绑定与独立记忆

制定日期：2026-11-05。状态：第 0～5 步的本地实现完成；固件升级及实物联调待完成。实际结果见[第二阶段联调记录](第二阶段联调记录.md)。

开发基线：`main` 分支提交 `5d810eb`；本地标签 `phase2-baseline-20261105`。

## 目标与范围

用现有的一台小猫完成“配置网络与服务器 → 登录账号 → 配对设备 → 正常对话 → 重启后延续记忆”的完整流程，同时通过模拟设备验证不同账号和设备之间的隔离。

本阶段添加六项能力：

1. 稳定的设备编号，以及独立、可撤销的设备连接凭证。
2. Wi-Fi、服务器地址、端口及连接协议的持久化配置。
3. 有效期有限、只能使用一次的设备配对码。
4. 简单的账号登录、设备列表、在线状态与控制页面入口。
5. 按设备隔离音频、画面、控制指令、模型会话和运行状态。
6. 将第一阶段聊天记忆接入真实的账号与设备身份。

首版每台设备同一时间绑定一个主人账号，一个账号可以拥有多台设备。对同一只小猫说话的人仍使用该主人账号的记忆。自动区分不同说话人、声纹和人脸识别留到后续阶段。

本阶段先完成本地开发和实物联调。云端部署另列执行步骤；暂不打包 exe、发布版本或增加 OTA。

## 开发基线的代码现状

- 主固件是 `firmware/esp32_servo_control/esp32_servo_control.ino`，约 3100 行，已有语音、摄像头、屏幕表情、四路舵机、配网和断线重连逻辑。
- 固件目前使用 `/ws/camera`、`/ws_audio` 和 `/stream.wav`；端口固定为 `8081`，服务器主机名可保存到 NVS。当前连接没有设备身份认证和 TLS。
- `server/app.py` 中的摄像头连接、音频连接、网页广播、翻译、视觉问答、动作及录制状态仍是单实例全局状态。
- `server/audio_stream.py` 中的播放任务、播放客户端和 PCM 预缓冲也共用。新播放请求会清理现有播放客户端，必须一起改造。
- `server/memory_store.py` 已按 `user_id` 与 `device_id` 存储记忆；`app.py` 仍使用固定测试身份。
- 第一阶段已有空闲五分钟总结、连接结束总结、正常关闭前冲刷以及下次启动补偿。
- Arduino ESP32 核心 `3.3.12` 和主固件直接依赖库已安装。当前安装不等于固件已经编译或上机验证通过。
- 前次设备识别结果为 ESP32-S3、8MB Flash。PSRAM 类型、实际连接端口和最终编译选项还需在实物操作前核对。
- 各草图配套的 `partitions.csv` 内容一致：一个约 2.5MiB 的程序分区和约 5.375MiB 的文件系统分区，没有第二个 OTA 程序分区。

## 实施步骤

### 0. 建立可恢复的实物基线

工作内容：

- 记录设备型号、Flash 容量、PSRAM 类型、串口及 Arduino 编译选项。
- 在首次写入设备前读取完整 Flash，保存 SHA-256、文件大小、芯片信息和分区信息。读 Flash 过程可能使设备短暂复位，实际操作前先说明命令和影响。
- 保存现有数据库的一致性备份；运行中的 SQLite 使用备份接口处理，避免只复制主文件而遗漏 WAL。
- 备份放在已忽略的 `artifacts/backups/`，不进入 Git。完整 Flash、数据库和配置可能包含网络凭据或聊天内容。
- 使用匹配的 8MB Flash、PSRAM 和自定义分区配置编译原始固件，记录结果和程序大小。通用开发板的默认 4MB、PSRAM 关闭配置不能作为本机的最终参数。

完成标准：备份可读、校验信息完整；原固件编译通过，或先记录并单独修复真实编译问题。此步骤不写入设备。

Git 保存：提交必要的开发说明；如有兼容性修复，每项单独提交。备份文件保留在本机。

### 1. 拆分设备运行状态

主要涉及：`server/app.py`、`server/audio_stream.py`，以及拟新增的设备运行状态模块。

工作内容：

- 建立以设备编号索引的运行状态容器，将摄像头、麦克风、网页连接、播放缓冲、模型会话及后台任务归属到具体设备。
- 将翻译、视觉问答、表情动作、手势跟随、屏幕状态和活动录制一起纳入设备范围。
- 各设备分别维护会话代次与清理逻辑，避免旧连接退出时清掉刚建立的新连接。
- 录制文件和图片按设备与会话存放；下载时检查数据归属。
- 程序配置、字体和只读模型文件可共享，用户内容与运行任务分别持有。
- 初期采用一个 Uvicorn worker，使同一设备的不同连接落在同一运行状态容器。多进程扩展需要额外的连接路由和状态协调，留到部署容量评估后安排。

完成标准：两个模拟设备同时运行时，重连、停止播放或重置其中一台，不影响另一台的画面、音频和任务。

计划提交：`refactor: 按设备隔离连接与音视频运行状态`。

### 2. 增加账号、设备登记与配对基础

主要涉及：拟新增的身份存储、认证路由和本机管理工具；为数据库引入有版本的迁移。

工作内容：

- 增加账号、登录会话、设备、设备凭证和配对请求数据。单台本地联调先沿用 SQLite；正式多人云端部署前另行安排数据库迁移与资源评估。
- 首版由本机管理工具创建测试账号并登记设备，供本人及朋友试用；公开注册、短信和邮件找回暂不加入。
- 账号密码使用成熟的 Argon2id 实现存储。网页登录采用可撤销的服务端会话，Cookie 配合过期策略、同源校验和写操作防伪造机制。
- 设备编号用于标识，独立的高强度随机凭证用于认证。首台设备通过受控的本机工具和 USB 配发凭证，服务端保存其摘要。
- 已登记的设备向服务器申请临时配对码，在设备本地页面显示。配对码有效期五分钟、一次有效，限制尝试次数和请求频率。
- 登录用户领取配对码时，服务器以登录会话确定主人身份，并用事务保证同一码只能成功绑定一次。
- 凭证支持撤销和重新配发；首版暂不提供设备转让及历史记忆自动转移。

完成标准：登录、退出、设备绑定可用；过期码、重复码、并发领取和错误凭证均有明确处理，凭证不出现在 URL、普通日志和 Git 中。

计划提交：账号与会话、设备登记与配对分别提交。

### 3. 让所有接口执行设备权限检查

主要涉及：`server/app.py`、`server/audio_stream.py` 及新增认证模块。

工作内容：

- 设备连接使用认证头；浏览器请求使用登录会话。服务器校验凭证、设备编号与绑定关系，不能依靠客户端提交的 `user_id` 决定数据归属。
- 统一保护麦克风、摄像头、播放流、复述音频、网页消息、记忆、舵机、屏幕、录制及图片读取入口。
- 新接口和 WebSocket 路径显式携带设备编号；`/api/devices/{device_id}/...` 与 `/ws/devices/{device_id}/...` 为拟采用的路径形式，具体子路径随实现记录。
- 将有副作用的 GET 控制请求改成经过认证的写操作，并同步更新网页调用。
- 旧接口同步改造或关闭，避免仍能访问原来的匿名播放流、控制接口和记忆调试接口。
- 设备解绑或凭证撤销后，终止对应连接和任务；对其他设备不产生影响。

完成标准：账号 A 和设备 A 不能读取、接收或控制设备 B；遗漏设备编号或认证失败时，不回退到固定测试设备。

计划提交：`feat: 为设备接口接入认证与归属检查`。

### 4. 接入真实身份与已有记忆

主要涉及：`server/app.py`、`server/memory_store.py` 及测试。

工作内容：

- 根据认证后的设备与绑定关系建立聊天会话，用真实 `user_id` 和 `device_id` 查询、保存和总结。
- 保留五分钟空闲总结、设备连接结束总结、服务正常关闭前冲刷及启动后的补偿。
- 突然断电由服务器在检测到断线或超时后安排总结；无法在设备断电瞬间可靠发送通知。仅已落库的消息可恢复。
- 异步总结使用原聊天会话的归属，避免重连或归属变化时把旧消息写给其他账号。
- 现有固定测试身份的数据先保留，提供显式、可重复检查的迁移步骤。备份并确认归属后再迁移，不把历史数据自动分给首个登录用户。
- 提供本人当前设备的记忆查看与清除入口；清除操作需要明确确认，数据库原始文件继续留在运行数据目录。

完成标准：同一设备重连或服务重启后可恢复上下文；不同测试账号与设备的摘要、近期消息和长期记忆互相隔离。

计划提交：真实身份接入与旧数据迁移分别提交。

### 5. 增加最小可用的账号与设备网页

主要涉及：`server/index_html.py`、网页路由，以及按需要新增的账号页面模块。

工作内容：

- 增加登录、退出、设备列表、配对码输入、在线状态和错误提示。
- 选择自己的设备后进入现有控制页面，页面请求和连接都固定到该设备。
- 保留已有对话、预览和控制功能，同步完成认证接口适配。
- 无权限或登录失效时停止敏感数据订阅，并引导重新登录。

完成标准：网页可完成“登录 → 添加设备 → 查看状态 → 进入控制台”，账号切换后不会保留上一账号的画面或聊天内容。

计划提交：`feat: 增加账号登录与设备管理页面`。

### 6. 升级固件并准备待烧录程序

主要涉及：`firmware/esp32_servo_control/`；本机设备登记工具与协议说明同步更新。

工作内容：

- 设备编号重启后稳定，编号和凭证分开存储；新增独立的身份配置区域，保留原有 Wi-Fi 配置与表情资源。
- 加入首次 USB 凭证配发、设备状态查询与配对码显示。普通配网页不展示长期设备凭证。
- 配网页支持服务器主机名、端口和协议，兼容读取旧主机名配置，避免旧的地址清洗逻辑丢掉端口和协议。
- 摄像头 WebSocket、音频 WebSocket 和 HTTP 播放流都使用同一设备身份和认证信息。
- 本地调试支持明确选择 HTTP/WS；云端连接使用 HTTPS/WSS、正确的证书校验及时间同步。连接失败时不自动降级为明文。
- 识别未绑定、凭证失效、服务器离线等状态，并控制重试频率。
- 保持现有接线、舵机角度限制、表情文件路径和 Flash 分区布局；删除源码中的真实网络凭据兜底。
- 记录加入 TLS 后的程序大小与内存开销。若超过现有程序分区或可用内存，先评估依赖和缓冲配置；调整分区涉及现有资源的保存与恢复，单独说明后处理。

完成标准：新固件编译通过，配置在重启后保留，生成的程序适配已核实的硬件和分区。实际烧录前展示备份结果、烧录文件、具体命令和影响，再确认执行。

计划提交：设备身份、服务器配置与认证连接按可验证步骤分别提交。

### 7. 单台实物联调与多设备模拟验证

工作内容：

- 烧录后验证配网、配对、语音对话、视觉问答、表情和舵机，核对原有功能是否退化。
- 验证连续空闲五分钟总结、设备关闭后的断线总结、服务器重启恢复，以及已落库消息的补偿。
- 用两个账号和两个模拟设备测试跨设备访问、播放流隔离、重连替换、配对码重放和凭证撤销。
- 用模拟模型响应执行自动化测试；真实 DashScope 对话只在实物联调中单独记录，避免把本地测试当作云端验证。
- 检查桌面源码的服务启动、停止和健康检查；受认证影响的测试使用受控测试身份适配。本阶段不重新打包 exe。
- 如出现硬件兼容性问题，按备份记录恢复现有设备，并保留问题与修复提交。

完成标准：下方验收项全部有对应的真实结果，尚未验证的项目如实保留。只有一台实物不影响本阶段开发；10～20 台同时使用的承载能力需在实际部署环境另行压测。

计划提交：联调修复与测试结果分别提交。

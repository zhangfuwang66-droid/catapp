## 拟写入内容与影响

只写 `app0` 主程序分区，起点 `0x10000`，上限 `0x280000`（2621440 字节）。不写启动程序、分区表、NVS 或 LittleFS；不执行全盘擦除，不使用 `merged.bin`。新固件挂载 LittleFS 时不会自动格式化。

设备将短暂重启，语音暂时中断；启动时会按原程序初始化舵机并回中位。请让小猫放在平稳位置，避免舵机受力，并保持供电和 USB 连接稳定。

原 Wi-Fi 和服务器配置在没有新版配置时继续读取。新身份使用独立 NVS 命名空间；新固件不会凭空生成服务器认可的凭证。写入后首先查询状态，再在实际后端登记编号和通过 USB 配发，最后配置账号模式与服务器地址。USB 配发和保存网络都会触发重启，需要事先说明并确认。

## 实际执行前的核对顺序

1. 检查 Git 提交、构建日志和新 `.bin` 校验值，确认镜像是 ESP32-S3、适配原分区，且没有在编译过程中修改源码。
2. 复核完整原机备份大小与 SHA-256，保留提取的原主程序和恢复说明。
3. 提前通知用户插入 USB；只读重新识别端口和芯片。连接 esptool 可能让设备短暂复位，也应告知用户。
4. 展示最终程序文件、实际 SHA-256、端口、写入起点与具体命令，取得用户确认。
5. 写入并核对工具报告的校验结果，再查询新版 USB 状态；错误时保留日志并先分析，不直接擦除或改分区。

## 待确认的命令示例

以下只展示计划。实际端口、文件与校验通过后才能执行：

```powershell
$esptool = 'C:\Users\20388\AppData\Local\Arduino15\packages\esp32\tools\esptool_py\5.3.1\esptool.exe'
$application = 'D:\Github\cat\catapp\artifacts\firmware\phase2-24d4cea4d1b4\application.bin'
Get-FileHash -LiteralPath $application -Algorithm SHA256
& $esptool --chip esp32s3 --port COM3 --baud 115200 --before usb-reset --after hard-reset --no-stub write-flash --flash-mode keep --flash-freq keep --flash-size keep --no-compress 0x10000 $application
```

`--no-stub` 沿用本机原备份时可用的 ROM 通道，速度可能较慢；如出现通信异常，先停止分析，不能直接改用全盘擦除解决。

## 烧录后的验收

- 检查屏幕、原表情资源、摄像头、音频与舵机，确认基本功能没有退化。
- 查询 USB 设备编号，验证重启后编号与配置保持；串口状态不泄露长期凭证和网络密码。
- 在实际后端登记此编号、配发凭证，验证未绑定状态、临时配对码、主人绑定、错误凭证和停用。
- 验证 HTTP 内网模式和受信任证书下的 HTTPS/WSS，检查麦克风、摄像头、播放流的认证与重连。
- 记录 TLS 连接前、连接后与语音/视频并发时的内部空闲堆、最低空闲堆、最大连续可分配块和 PSRAM；编译期静态内存数字不能替代实测。
- 验证真实模型协议、正常聊天、空闲五分钟总结、断线总结和服务重启后的记忆恢复。模型模拟测试不能代表真实语音可用。
